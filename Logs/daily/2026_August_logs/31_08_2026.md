This session continued the internal architectural refactor of Anneal V1, with the goal of making the model explicit about its own state generation rather than relying on main.py to construct or manage intermediate model mechanisms.
The refactor successfully progressed through branch generation → branch transformation → branch out → Alpha weighting, leaving Alpha weighting as the final mechanism before the model outputs.
MLPBranch Responsibility
MLPBranch was clarified as the owner of the initial branch transformation.
Input:
branch_embed
    [number_of_branches, state_dimension]
Current configuration:
55 branches × 3 state dimensions
The MLP transformations produce the intermediate branch representation internally.
Conceptually:
branch_embed
    ↓
MLP1
    ↓
MLP2
    ↓
x
x is the transformed branch representation.
The MLP does not own the later temporal or channel dimensions.
Model Responsibility
Anneal_State_Generation now owns the downstream construction of the state.
The model internally calls MLPBranch rather than requiring main.py to call the branch network independently.
The intended flow is now:
main.py
    ↓
Anneal_State_Generation.forward()
    ↓
MLPBranch.forward()
    ↓
branch transformation
    ↓
step progression + channels
    ↓
branch_out
    ↓
trajectory formulation
    ↓
Alpha weighting
    ↓
positional_prediction
    ↓
return
main.py should therefore become increasingly thin: it should call the model and consume its output rather than manually reconstructing internal model states.
Branch Expansion
The transformed MLP output begins as:
[55, 3]
The trajectory formulation requires:
[55, 20, 4, 3]
where:
55 = branches
20 = steps/divergences
4 = channels
3 = state dimensions
The important distinction discovered during debugging:
reshape/view cannot create missing information or dimensions.
The branch representation must first be expanded/broadcast into the required step/channel structure.
The architectural ownership is therefore:
MLPBranch:
    [55, 3]

Model / trajectory formulation:
    [55, 20, 4, 3]
This successfully restored the expected structure and allowed execution to progress through branch out.
Per-Forward State
Several quantities were clarified as model-owned, per-forward state rather than permanent parameters.
These include:
delta
theta_d
P_d
positional_delta
Each forward/step begins from its appropriate reset state.
Important distinction:
model-owned parameter
    ≠
per-forward tensor
For tensors created from scratch, the model's device should be used:
device = next(self.parameters()).device
This should generally be established once within the relevant scope rather than repeatedly before every tensor.
Model-produced tensors already inherit the device from the operations producing them.
Device Ownership
A useful rule established during the refactor:
Existing model output generally does not need manual device assignment. Newly created tensors do.
For example:
device = next(self.parameters()).device

delta = torch.zeros(3, device=device)
This avoids repeatedly coupling unrelated state tensors to an arbitrary layer such as mlp1.weight.device.
The various state mechanisms can instead use the device associated with their actual owning model/layer.
Parameter vs. Runtime Control
The distinction between architectural parameters and runtime controls was also clarified.
For example:
bias=False
is a property of a linear layer and means the layer has no learned bias term.
Whereas:
update_rule=None
channels=None
can function as explicit runtime interface controls.
None can represent:
no override/configuration supplied; use the model's default behavior.
This provides a clean path toward future channel routing and other control mechanisms without forcing main.py to manage internal wiring.
Channel Concept
channels can eventually become a routing/configuration mechanism.
For example:
channels
├── branch
├── delta
├── theta
└── position
The important architectural principle is:
A caller supplies channel configuration; the model interprets it.
This keeps routing logic inside the model rather than turning main.py into a wiring harness.
Delta / Theta / P_d Ownership
The distinction between these quantities became clearer:
P_d → step trigger / model-owned
delta → generated through delta_readout
theta_d → generated through theta mapping
delta_readout is the mechanism that produces delta; the resulting delta tensor is not the same thing as the layer that generates it.
This avoided the earlier naming/device confusion where a tensor was incorrectly treated as though it were its generating layer.
Major Debugging Discovery
An important shape error exposed an architectural boundary:
x = [55, 3]
was being forced into:
[55, 20, 4, 3]
without first creating the required step/channel structure.
The problem was not that the MLP output was wrong.
The problem was that the downstream trajectory formulation was still expecting structure that had previously been implicitly created elsewhere.
This distinction helped preserve the cleaner architecture:
MLP produces branch state.

Trajectory formulation produces temporal/channel structure.

Next Phase: Architectural Stress Testing
Once a clean forward pass is achieved, the next step is to freeze that version as a baseline before making further architectural changes.
The model can then be provided independently to multiple blind model sessions, excluding main.py and unrelated implementation files.
Each model can independently evaluate:
1. Inference
What can be inferred about the architecture from the model alone?
2. Ambiguity
Where can the code reasonably be interpreted in multiple ways?
3. Data Flow
Can the transformation from inputs to outputs be reconstructed?
4. Ownership
Are state, parameters, transformations, and routing responsibilities located in sensible components?
5. Redundancy
Is any code duplicated or performing work that is no longer necessary?
6. Placement
Are mechanisms located in the correct class/function?
7. Shape Semantics
Do tensor dimensions correspond to their apparent conceptual meaning?
8. State Semantics
Which quantities are persistent parameters and which are regenerated each forward/step?
9. Interfaces
Are the boundaries between model components explicit and understandable?
10. Failure Modes
What assumptions or edge cases could cause unexpected behavior?
The purpose is not to ask the external models to redesign Anneal.
The purpose is to determine:
What does the architecture communicate
when its creator does not explain it?
Disagreement between models can then be categorized as:
model misunderstanding
        vs.
actual architectural ambiguity
        vs.
intentional unusual design
        vs.
real implementation bug
This creates a form of multi-architect debugging while preserving the original architecture as the baseline.
