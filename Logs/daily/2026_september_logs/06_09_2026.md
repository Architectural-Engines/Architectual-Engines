06_09_2026:

**Parameter-Space Archaeology: Discovering Existing Complexity**

**Core insight**

Anneal parameter exploration should not be treated merely as numerical tuning.

**The more useful interpretation is**:

Not adding complexity, but discovering what complexity already exists.

Changing a parameter can expose different computational regimes that are already latent in the architecture. The goal is therefore to map the existing response landscape before deciding what values are “correct.”

**Initial observation**

**Several state-related vectors were initially initialized as**:

positional_delta = [0, 0, 0]
delta = [0, 0, 0]
theta_d = [0, 0, 0]

**Controlled probes showed that these zeros are not necessarily computationally neutral**.

Setting "theta_d" to:

[1, 1, 1]

**activated a previously suppressed imaginary interaction pathway**.   <---important

Setting:

delta = [1, 1, 1]
theta_d = [1, 1, 1]
PD = [0, 0, 0]

production of low-loss regime.

delta, theta_d, PD to "[1,1,1]" produced  dramatically different, **high-variance regime, results substantially worse**.

Established parameters: not interchangeable interaction matters.

Positional delta probe

**informative experiment changing only**:

PD = [0, 0, 0]

to:

PD = [0.0001, 0.0001, 0.0001]

and subsequently:

PD = [0.0033, 0.0033, 0.0033]

The "0.0033" condition produced:

**loss ≈ 0.002606**
**PD magnitude ≈ 0.005716**
**generated state magnitude ≈ 2.008**
**generated state std ≈ 0.01727**
**prediction std ≈ 0.04574**
**branch variance mean ≈ 0.00855**
**uncertainty mean ≈ 0.04964**

For comparison, earlier unit-scale condition produced substantially larger space and branch variance.

The observation suggests that a small nonzero positional perturbation may place the system into a narrow, low-variance interaction regime, while a unit-scale perturbation produces a much broader regime.

**This does not establish** that "0.0033" is the correct value.

establishes: the response to positional delta contains structure worth mapping.

**Interaction geometry**:

probe showed a separation between interaction magnitude/resolved state magnitude.

**For the "PD = 0.0033" condition**:

interaction imaginary std ≈ 2.052
generated-state std ≈ 0.0173

**system transformations appears relatively broad**: interaction representation into a much more concentrated generated state.

Exact mechanism responsible for this compression, needs to be traced in code.

Search-space hypothesis

**working hypothesis**:"positional_delta" functions more like a small positional aperture than a large displacement.

**Conceptually**:

PD = 0
    ↓
no positional perturbation

small PD
    ↓
narrow search aperture

large PD
    ↓
expanded interaction/search region

This remains a hypothesis.

**correct next step**: not to assume the interpretation, but to measure how the system responds as the parameter changes scale.

Experimental strategy

The parameter space should first be explored broadly:

PD
delta
theta_d

using substantially different magnitudes and combinations.

Potential probe values include:

0
0.0001
0.0003
0.0033
0.0333
0.3
1
1.3
3.0
3.14159

These values are probes, not presumed meaningful constants.

The purpose is to determine whether the system contains:

- stable regions
- high-variance regions
- transition thresholds
- compressed representations
- multiple low-loss regimes
- nonlinear responses
- parameter interactions
- directional sensitivities

Two stages of investigation

1. Landscape discovery

Change parameters broadly to determine what regimes already exist.

parameter perturbation
        ↓
interaction response
        ↓
distribution change
        ↓
observable regime

At this stage, the objective is exploration rather than optimization.

2. Causal characterization

Once an interesting region is discovered, return to controlled one-variable experiments.

interesting regime
        ↓
hold everything constant
        ↓
change one parameter
        ↓
measure response

This separates parameter effects from parameter interactions.

What to measure

Loss alone is insufficient.

Each probe should preserve the same instrumentation where possible:

parameter values
PD magnitude
delta magnitude
theta_d magnitude

interaction_real
interaction_imaginary

uncertainty

branch variance
branch variance mean

generated-state magnitude
generated-state mean
generated-state std

positional prediction
prediction distribution

loss

The purpose is to determine how the internal distributions reorganize, not simply which parameter produces the smallest scalar loss.

Important distinction

A low-loss parameter combination does not automatically mean that each individual parameter is correct.

For example:

PD = 0.0033
delta = 1
theta_d = 1

only demonstrates that this combination produces an observed regime.

It does not establish:

PD = correct
delta = correct
theta_d = correct

because the parameters may interact nonlinearly.

Therefore:

«A successful configuration is evidence of a regime, not proof of individual parameter meaning.»

Tuning as cartography

The resulting approach changes the meaning of tuning.

Traditional tuning:

find parameter
      ↓
minimize loss

Parameter-space archaeology:

existing architecture
        ↓
parameter perturbation
        ↓
observe computational response
        ↓
map existing regimes
        ↓
identify structure
        ↓
characterize causal effects
        ↓
tune within discovered structure

The architecture is not being made more complicated.

Its existing complexity is being interrogated.

Working principle

**Do not add complexity until the existing architecture has been sufficiently explored to determine whether the behavior already exists.**

**06_09_2026 SESSION B**

second coding session clarified architectures computational topology. end-to-end executions remaining problems are primarily boundary/plumbing/autograd issues, rather than broad architectural uncertainty.

1.**Core architectural distinction: persistent parameters vs generated state**

**model's learned parameters and transformation layers persist across forward passes**

persistent learned weights

        ↓

     transform

        ↓

runtime generated state

generated state is runtime data. It should not be confused with the persistent .weight of a learned layer.

persistent nn.Linear can transform runtime state, but its weights remain part of the model.

resolves an earlier architectural problem where linear layers were being instantiated inside forward(), causing their parameters to be recreated rather than persist as stable transformations.

Important distinction

persistent parameter

    = learned transformation


generated state

    = current computational state/update


trajectory

    = process/history representation

This supports the emerging idea that Anneal does not necessarily need to preserve a literal trajectory tensor indefinitely. A trajectory may be an ephemeral process whose consequences become part of subsequent state updates.

2. **Forward topology is now much clearer**

The current computational path is approximately:

branch embedding

      ↓

branch update

      ↓

velocity real / velocity imaginary

theta real / theta imaginary
      ↓
complex denominator
      ↓
number real ← positional latent

number imaginary ← delta
      ↓
complex interaction
      ↓
interaction real / interaction imaginary
      ↓
alpha-weighted branch aggregation
      ↓
latent real / latent imaginary
      ↓
uncertainty
      ↓
positional projection
      ↓
positional prediction

Current major tensor shapes include:

branch_out              [55, 20, 4, 3]


velocity real/imag      [55, 20, 3]

theta real/imag         [55, 20, 3]


number real/imag        [55, 20, 3]


interaction real/imag   [55, 20, 3]


latent real/imag        [55, 20, 3]


uncertainty             [55, 20]


positional prediction    [55, 20, 3]


generated state          [55, 20, 4, 3]

The 55 dimension is the branch dimension and 20 is the current inner progression/step dimension.

These dimensions should not be casually collapsed merely to satisfy a visualization or loss shape.

3. Alpha is computationally positioned correctly

Alpha was traced more carefully.

Alpha is not a post-interaction correction.

Its intended location is within the branch interaction aggregation:

velocity/theta

      ↓

complex interaction

      ↓

interaction real/imag

      ↓

alpha normalization

      ↓

branch aggregation

Current alpha implementation has effectively one normalized scalar:

branch_logits [1]

    ↓

softmax

    ↓

alpha [1]

    ↓

normalization [1,1,1,1]

The alpha normalization currently evaluates numerically to 1.

Earlier alpha tensors participated in autograd, but after the recent changes the currently observed alpha tensors can be graph-free.

This should not be “fixed” blindly. The intended question is whether alpha is supposed to be trainable or intentionally fixed during the behavior probe.

4. Epsilon is a scalar control, not a spatial state

Epsilon is a Python float:

self.epsilon = epsilon

and enters the denominator calculation as:

denom_mag2 = (

    denom_real**2

    + denom_imaginary**2

    + eps_effective**2

)

epsilon has no tensor dimensions or degrees of freedom of its own.

ability to affect tensor interaction: through participation in the denominator.

Useful example of the distinction between:

parameter/control representation

vs.

spatial tensor representation

6. Generated state became more important than trajectory

A major conceptual shift occurred during this session.

Instead of assuming:

trajectory → must be preserved

the emerging architecture can be viewed as:

step

 ↓

state update

 ↓

generated state

 ↓

next state update

**The trajectory may be an ephemeral process used to generate or expose state.**

**The generated state can instead become the substrate for persistence.**

**This leads to a potentially important distinction**:

trajectory persistence

≠

state persistence

**A system might discard the literal trajectory while preserving the consequences of its computation through persistent learned transformations and subsequent state updates.**

7.**Outer step vs inner progression**

**The current code uses an outer iteration such as**:

for epoch in range(epochs):

where earlier versions contained trajectory-oriented iteration.

The current evidence suggests the 20 dimension inside:

[55,20, ...]

is an inner progression rather than simply 20 simultaneous representations of one state.

This distinction remains important.

Do not restore old trajectory handling merely because the word trajectory existed in V1.

Instead, recover what each old trajectory axis actually represented.

8. Loss plumbing became the final problem

The model's forward contract is now conceptually:

model(...)

    ↓

prediction

delta

uncertainty

generated_state

Training then computes:

prediction

    ↓

loss function

    ↓

scalar loss

The scalar loss is the object that should participate in:

loss.backward()

The visualization/evaluation layer should receive a reporting-safe representation of the loss.

The recent visualization error was:

AttributeError:

'tuple' object has no attribute 'item'

at:

loss.item()

This means the object called loss at visualization time is currently a tuple rather than a scalar tensor.

The likely boundary problem is:

loss = train_on_synthetic(model)

combined with a changed return contract somewhere inside train_on_synthetic().

The correct architecture to investigate is:

model

 ↓

multiple outputs


train_on_synthetic

 ↓

compute scalar loss

 ↓

backward

 ↓

return scalar loss


main

 ↓

owns returned loss

 ↓

passes loss to evaluation/visualization

Do not have evaluation secretly invoke training merely to obtain the loss.

9. Detach belongs after the training dependency

A previous issue was identified where positional_prediction had been detached before the loss calculation.

That produced:

prediction.requires_grad = False

prediction.grad_fn = None


loss.requires_grad = False

loss.grad_fn = None

and ultimately:

RuntimeError:

element 0 of tensors does not require grad

and does not have a grad_fn

The conceptual correction is:

model prediction

      ↓

differentiable loss

      ↓

backward()

      ↓

detach for reporting/visualization

So the training loss should remain connected to the autograd graph until after backward().

The visualization copy can be detached.

The exact implementation should be rechecked fresh next session rather than patched from memory.

10. Shape warning remains separate from autograd

A previous warning showed:

target: [3]

input:  [55,20,3]

This is a separate issue from whether loss has a valid autograd graph.

The shape mismatch should not be “fixed” by arbitrary reshaping.

The actual intended contract between:

positional_prediction

and:


still needs to be explicitly established.

The fact that the prediction currently contains branch and progression dimensions is potentially meaningful architectural information.


architecture

    ↓

forward computation

    ↓

runtime state

    ↓

training objective

    ↓

evaluation/reporting
