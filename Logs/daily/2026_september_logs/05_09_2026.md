Major Architectural Discovery

The old variable called:

trajectories

appears to correspond to what is now called:

generated_state

The current structure is approximately:

generated_state = []



generated_state.append(branch_out)

where:

branch_out

    ↓
branch update

    ↓
branch logits

The important realization:

branch_out
    = branch/state update

generated_state
    = accumulated generated states

The current model was generating generated_state, but it was effectively going nowhere.

It was not being returned from forward().

The likely missing plumbing is therefore:

branch update
      ↓
branch_out
      ↓
generated_state.append(...)
      ↓
generated_state
      ↓
forward() return
      ↓
main
      ↓

visualization

rather than trying to construct the trajectory directly from branch_out.

Important Loop Discovery

The old code had something resembling:

for traj_idx, trajectory in enumerate(trajectories):

This was removed and replaced with:

for epoch in range(epochs):

That replacement may have conflated two different concepts.

epoch

= training iteration


trajectory index
= generated-state / trajectory instance



Current Model Output Contract

Previously the model returned:

prediction

positional_delta

uncertainty

Conceptually:

prediction [55,20,3]

delta [3]

uncertainty [55,20]

The model now needs to expose generated_state if the visualization is supposed to inspect it.

Potential return:

return positional_prediction, positional_delta, uncertainty, generated_state

Then main can unpack:

positional_prediction, positional_delta, uncertainty, generated_state = model(...)

This has NOT yet been fully wired through and visualized.

Current Conceptual Pipeline

The emerging architecture is:

branch logits

      ↓
branch update
      ↓
branch_out
      ↓
generated_state
      ↓
state history / trajectory substrate
      ↓
trajectory visualization
Separate from:
latent state
      ↓
uncertainty
      ↓
uncertainty visualization
And separately:
prediction
      ↓
target / positional delta
      ↓
loss

This explains how the model can have:

excellent loss,

stable uncertainty,

correctly generated states,

while the visualization still fails to show the trajectory: the generated state exists internally but wasn't exposed to the visualization.

The model is currently being invoked with:

motion_type=None

and appears to fall back to linear behavior.

The resulting uncertainty points therefore form a straight-line structure.

This suggests motion type may need to be explicitly identified rather than implicitly defaulted.

Potential conceptual pipeline:

      ↓
uncertainty
      ↓
visualization

This led to the realization:

Anneal needs identifiers.

This should remain an open architectural hypothesis, not yet treated as established implementation.

9. New hypothesis: feedback of generated distributions

A new architectural question emerged from the instrumentation.

Current mechanism appears conceptually similar to:

real state
    \
     interaction → output → prediction
    /
imaginary state

The question is whether the interaction output/distribution can be fed back into the existing mechanism before producing the final prediction.

Conceptual experiment:

initial existing state
        ↓
interaction
        ↓
distribution/state₀
        ↓
feedback
        ↓
interaction
        ↓
distribution/state₁
        ↓
feedback
        ↓
...
        ↓
prediction
        ↓
loss
        ↓
training

This would create internal evolution within a single forward pass.

Important distinction:

Feedback iterations are not training epochs.

Training would remain:

epoch
  ↓
model forward
  ↓
internal state evolution
  ↓
prediction
  ↓
loss
  ↓
backpropagation
  ↓
parameter update

while internal evolution would be:

state₀
 ↓
interaction₀
 ↓
state₁
 ↓
interaction₁
 ↓
state₂
 ↓
prediction

10. Do not implement feedback yet

A placeholder implementation was discussed using hypothetical variables such as:

initial_state
feedback_steps

These variables do not currently exist in Anneal.

They were conceptual placeholders only.

Before implementing feedback:

1. Locate the actual tensor entering the interaction mechanism.
2. Locate the actual interaction operation.
3. Identify the output of that operation.
4. Determine whether that output can legitimately be fed back into the same mechanism.
5. Identify the first point where imaginary information becomes zero.
6. Determine whether the generated state already represents the intended feedback state.

Do not invent a new "initial_state" abstraction until the existing architecture reveals what its initial state actually is.

Do not introduce "feedback_steps" until the mechanism being repeated has been identified.
